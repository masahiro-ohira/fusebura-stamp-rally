# 開発メモ

## 現在のシステム構成

- [index.html](../index.html) はスタンプラリーの画面とブラウザ側の処理を担当します。会場5か所と店舗20か所を定義し、QRコードなどから開いたURLの `spot` を使って取得処理を開始します。参加者IDはURLの `pid` を優先し、ブラウザのローカルストレージにも保存します。
- [functions/api.js](../functions/api.js) は Cloudflare Pages Functions の `/api` を担当します。`GET` は参加者の履歴を取得し、`POST` はスタンプ取得または履歴リセットを処理します。
- API は `env.DB` 経由で Cloudflare D1 の `participants`、`spots`、`stamps` を参照します。D1 のスキーマやマイグレーションはリポジトリに含まれていません。

スタンプ取得時、API はスポットの存在と有効状態を確認してから取得順を付けて保存します。同じスポットの連続取得は拒否します。間に別のスポットを挟んだ再訪問は履歴に記録され、画面の進捗と達成判定では同じスポットを1か所として数えます。

ページを開くと D1 から履歴を取得し、取得に失敗した場合はローカルストレージの履歴を表示します。リセットは対象参加者のスタンプ行を削除し、成功後にブラウザの履歴キャッシュを消します。参加者IDは再利用されます。

## セキュリティ上の課題

- 履歴取得・スタンプ登録・リセットでは、リクエストに含まれる参加者IDを処理対象にしています。API に本人性や操作権限を検証する処理がないため、履歴の閲覧・変更・削除を参加者本人に限定できません。リセットボタンの確認ダイアログは画面上の誤操作を防ぐためのものです。
- 履歴のキャッシュは参加者別に分かれていません。同じブラウザで参加者IDを切り替え、D1 からの読み込みが失敗した場合、以前の参加者の履歴が表示される可能性があります。

## 同時アクセス時の課題

直前の取得の確認、次の取得順（`MAX(scan_order) + 1`）の計算、新しいスタンプ行の挿入は別々のSQL文で実行されます。同一参加者の取得リクエストが重なると、両方が同じ直前履歴や取得順を参照する可能性があります。その場合、API の処理だけでは連続取得の拒否や取得順の一意性を保証できません。実際の動作は D1 側の制約にも依存し、本番のスキーマや同時アクセス時の挙動は未確認です。
